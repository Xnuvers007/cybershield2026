🔑 IDOR — A01:2026

Cara Kerja IDOR

Ubah ID di URL/parameter → akses data user lain tanpa otorisasi. Bagian dari Broken Access Control.

← Broken Access🏠 Semua AnimasiAuth Failures →
1
👤 User login dan akses data sendiri
User login → akses profil/invoice di URL: /api/invoice/1001. ID 1001 adalah invoice milik user ini.
2
🔢 Attacker melihat pattern ID
ID sequential (1001, 1002, 1003...) mudah ditebak. Penyerang mencoba mengubah ID:
/api/invoice/1002 → Invoice user lain?
3
📄 Server mengembalikan data tanpa auth check
Server TIDAK memeriksa apakah invoice 1002 milik user yang sedang login. Data user lain langsung dikembalikan!
4
🤖 Automasi dengan Burp Intruder
Penyerang menggunakan tools untuk iterate semua ID: 1001-9999. Download massal semua invoice/data.
5
💥 Data breach massal
Semua invoice, profil, dokumen pribadi user terekspos. KTP, alamat, data keuangan — semua bocor.
1 / 5
⚠️ RENTAN
$id = $_GET['id']; $invoice = getInvoice($id); echo json_encode($invoice); // Ubah id=1001 → id=1002 // → Lihat invoice user lain!
✅ AMAN
$id = $_GET['id']; $invoice = getInvoice($id); // Cek apakah milik user ini! if ($invoice['user_id'] !== $_SESSION['uid']) { http_response_code(403); die('{"error":"Forbidden"}'); } // + Gunakan UUID bukan sequential ID

💀 Dampak

  • Data breach massal (iterate IDs)
  • Akses dokumen pribadi user lain
  • Financial data exposure
  • Compliance violation (GDPR, PDP)

🛡️ Pencegahan

  • Authorization check SETIAP request
  • UUID bukan sequential integer
  • Row-level security di database
  • Automated IDOR testing
